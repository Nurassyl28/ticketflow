# План разработки TicketFlow

Основа: [исходное ТЗ](spec.md). Разработка начата.
Этап 1 завершён: FastAPI, окружение `uv`, PostgreSQL, проверки API и CI.
Следующий этап — модель БД и миграции.

## Результат первого релиза

Покупатель находит мероприятие, выбирает места, получает бронь на 10 минут,
оплачивает заказ через mock payment и получает QR-билеты. Организатор управляет
своими мероприятиями, проверяет билеты и видит продажи. Параллельные запросы
не приводят к двойной продаже места.

Стек из ТЗ: FastAPI и PostgreSQL. Управление Python — через `uv`.
Для первого релиза планируется backend REST API; интерфейс сайта и реальная
платёжная система — возможные отдельные этапы после него.

## Предлагаемые уточнения ТЗ

Ниже — проектные решения для реализации, а не изменения исходного документа.
Уточнения соответствующего этапа фиксируем в его issue до написания кода.

| Пробел | Предлагаемое решение | Этап |
| --- | --- | --- |
| Нет `events.category`, хотя есть фильтр | Добавить категорию события; определить набор значений | 2 |
| Нет владельца площадки и API настройки зала | Добавить `venues.organizer_id`; CRUD площадок, секций и мест; после открытия продаж запретить изменение проданной схемы | 2, 4 |
| Нет строки для блокировки ещё свободного места конкретного события | Создавать `event_seats` с уникальной парой `(event_id, seat_id)`; связать место с тарифом того же события и секции | 2, 5 |
| В запросе брони несколько мест, в таблице — одна строка на место | Добавить общую группу брони с владельцем и единым `expires_at`; все места бронируются целиком либо запрос откатывается | 2, 5 |
| Заказ не связан с бронью, цены могут измениться | Связать заказ с группой брони, разрешить один заказ на группу; добавить `order_items` со снимком цены и типа билета | 2, 6 |
| Не определены деньги и время | Для MVP предложена одна валюта KZT; цены — точный десятичный тип, не float; время — timezone-aware UTC, отображение отдельно | 2 |
| Нет API входа, отмены и получения билетов | Добавить регистрацию/вход, отмену заказа, получение своих билетов; точные маршруты описать в issue | 3, 7, 8 |
| Не определены полномочия ADMIN и проверяющего QR | ADMIN назначает организаторов и отменяет события; билеты проверяет организатор соответствующего события либо ADMIN | 3, 7, 8 |
| Нет правил повторной оплаты | Уникальный ключ операции и сохранённый результат; mock-оплата всегда проверяет владельца, сумму на сервере и срок брони | 6 |
| Не задана политика отмены и возврата | Предложение: до начала события — полный mock-возврат неиспользованного заказа; использованные билеты блокируют отмену покупателем; отмена события возвращает оплату и аннулирует билеты | 8 |
| DELETE события может уничтожить историю покупок | Удалять только черновик без продаж; остальные случаи переводить в CANCELLED с сохранением истории | 4, 8 |
| Не определены формулы аналитики | `tickets_available` исключает продажи и активные брони; выручка учитывает возвраты; правила остальных метрик и часовой пояс фиксируются в issue | 9 |

## Как защитим бронирование

| Правило | Реализация в плане |
| --- | --- |
| Одно место относится к конкретному событию | Занятость хранится на уровне `(event_id, seat_id)`, а не физического места площадки |
| Два покупателя не получают одно место | Короткая транзакция блокирует существующие `event_seats` через `SELECT ... FOR UPDATE`, повторно проверяет занятость и создаёт бронь |
| Нет транзакции длиной 10 минут | После записи брони транзакция заканчивается; срок удержания задаёт `expires_at` |
| Нет частичной брони и конфликтующего порядка блокировок | Все запрошенные места блокируются в одном фиксированном порядке; ошибка откатывает всю группу |
| Просроченное место можно купить сразу | Срок проверяется при бронировании и оплате под блокировкой; фоновая задача лишь приводит сохранённые статусы в порядок |
| Оплата, истечение и отмена согласованы | Все операции используют общий порядок блокировок; выпуск билетов, статусы заказа/брони и mock-платёж фиксируются атомарно |
| БД защищает от дублей | Уникальные ограничения на пару событие/место в инвентаре, один действующий или использованный билет на эту пару, заказ группы и ключ оплаты; внешние ключи защищают связи |
| QR используется один раз | Проверка и переход `VALID → USED` выполняются атомарно; одновременные сканирования дают один успех |

Основа для плана блокировок — документация PostgreSQL: [row-level locks](https://www.postgresql.org/docs/current/explicit-locking.html#LOCKING-ROWS)
и [constraints](https://www.postgresql.org/docs/current/ddl-constraints.html).
Выбор `event_seats` и границ транзакций — предложенная архитектура TicketFlow.

## Обязательные проверки перед первым релизом

| Сценарий | Ожидаемый результат |
| --- | --- |
| Два покупателя одновременно бронируют одно место | Одна успешная бронь, второй получает конфликт |
| Одно из нескольких мест уже занято | Остальные места запроса не удерживаются |
| Одинаковое физическое место на разных событиях | Брони независимы |
| Истечение брони одновременно с оплатой | Либо одна завершённая покупка, либо отказ; оплаченного заказа без билетов нет |
| Фоновая задача задержалась | Просроченную бронь нельзя оплатить; место можно забронировать снова |
| Повтор запроса оплаты или возврата | Сохраняется единственный результат операции |
| Два одновременных сканирования QR | Один успех, один отказ |
| Чужой заказ, событие или билет | Доступ запрещён |
| Отмена одновременно с покупкой | После отмены события новые действительные билеты не остаются |
| Dashboard после продажи и возврата | Метрики совпадают с заказами и билетами в БД |

Конкурентные проверки выполняются на настоящей PostgreSQL, с отдельными
соединениями и согласованным одновременным запуском операций.
