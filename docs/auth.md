# Вход и права доступа

Этап 3, [issue #7](https://github.com/Nurassyl28/ticketflow/issues/7).
Создание и изменение каталога описано в [catalog.md](catalog.md), создание заказов — этап 6.
Здесь уже работают регистрация, сессии, назначение ролей и защищённое чтение.

## Маршруты

| Метод и путь | Доступ и результат |
| --- | --- |
| `POST /auth/register` | Без токена; email и пароль; `201` с профилем CUSTOMER |
| `POST /auth/login` | Без токена; email и пароль; `200` с `access_token`, `token_type`, `expires_in` в секундах |
| `GET /auth/me` | Текущий профиль по Bearer-токену |
| `POST /auth/logout` | Удаление текущей сессии; `204` |
| `GET /orders/me` | Заказы текущего пользователя, для любой роли |
| `GET /orders/{order_id}` | Заказ текущего пользователя; чужой или отсутствующий — `404` |
| `GET /organizer/events` | ORGANIZER: свои события, включая черновики; ADMIN: все |
| `GET /organizer/events/{event_id}` | То же ограничение владельца; чужой или отсутствующий — `404` |
| `GET /organizer/venues` | ORGANIZER: свои площадки; ADMIN: все |
| `GET /organizer/venues/{venue_id}` | То же ограничение владельца; чужая или отсутствующая — `404` |
| `PATCH /admin/users/{user_id}/role` | ADMIN назначает другому пользователю CUSTOMER или ORGANIZER |

Списки принимают `limit` от 1 до 100 (по умолчанию 50) и `offset` от 0.
CUSTOMER получает `403` на маршрутах организатора. Даже ADMIN видит через `/orders`
только собственные заказы. Публичный каталог доступен без токена через `/events`.

## Проверка в Swagger UI

1. Примени миграции: `uv run --locked alembic upgrade head` и запусти API по README.
2. Открой `http://127.0.0.1:8008/docs` и вызови `/auth/register` с JSON
   `{"email":"your-email@example.com","password":"replace-with-your-password"}`.
   Замени оба значения своими. Пароль — 12–128 символов; email сохраняется в нижнем регистре.
3. Вызови `/auth/login` с теми же данными. В **Authorize** вставь только значение
   `access_token`; Swagger добавит `Authorization: Bearer <token>`.
4. Проверь `/auth/me`, затем `/auth/logout`. Следующий запрос с тем же токеном вернёт `401`.

Регистрация не принимает `role` и `password_hash`; лишние поля дают `422`.
Повторный email, включая другой регистр букв, даёт `409`. Неизвестный email,
неверный пароль и отключённая учётная запись при входе дают одинаковый `401`.
Ответы валидации не включают исходные значения пароля.

## Сессии и пароли

| Свойство | Реализация |
| --- | --- |
| Пароли | Argon2id через `pwdlib`; параметры устаревшего хеша обновляются при успешном входе |
| Токен | 32 случайных байта, URL-safe строка; передаётся в заголовке Authorization |
| Хранение | В `auth_sessions` сохраняется только SHA-256 токена |
| Срок | `AUTH_TOKEN_TTL_MINUTES=15`, допустимо 1–120; срок сверяется со временем PostgreSQL |
| Выход | Отзывает текущую сессию; другие входы продолжают работать |
| Истечение | Просроченный токен даёт `401`; пользователь входит заново, автоматического продления нет |
| Изменение роли | Следующий запрос использует актуальную роль из БД, перевыпуск токена не требуется |
| Отключение | Хеш пароля с префиксом `!` блокирует вход и использование уже выданной сессии |

Seed-пользователи `*@demo.ticketflow.invalid` отключены. Для работы через API
регистрируй отдельные учётные записи. Истёкшие сессии остаются в БД, но не дают доступ;
периодическая очистка пока не добавлена.

## Назначение ролей

Первого администратора назначает оператор с локальным доступом к приложению и БД.
Сначала зарегистрируй пользователя, затем выполни:

```sh
uv run --locked python -m ticketflow.manage promote-admin your-email@example.com
```

Команда не создаёт пользователя и не активирует seed-аккаунты. Повторный запуск
для ADMIN ничего не меняет. Назначение записывается в `audit_logs` как системное действие.

ADMIN вызывает `PATCH /admin/users/{user_id}/role` с `{"role":"ORGANIZER"}`
или `{"role":"CUSTOMER"}`. Нельзя изменить свою роль, другого ADMIN или назначить
ADMIN через HTTP. Изменение роли и запись аудита фиксируются одной транзакцией;
повтор того же значения не создаёт новую запись.

## Использование в следующих этапах

`CurrentUser`, `Manager` и `Administrator` — зависимости FastAPI для авторизации.
`get_owned_order`, `get_managed_event` и `get_managed_venue` ограничивают доступ
владельцем. Новые маршруты изменения ресурсов должны использовать эти проверки
до изменения данных; владение определяется сервером по текущему пользователю.

Проверки выполняются на PostgreSQL: чужие ресурсы, все роли в матрице доступа,
истечение и отзыв токена, отключённые аккаунты, попытки повышения роли,
немедленное применение новой роли и отсутствие паролей в ответах.
