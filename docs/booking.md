# Бронирование

`POST /reservations` принимает `event_id` и массив `seat_ids` из 1–20 уникальных UUID.
Нужен Bearer-токен. Ответ `201`: `id` группы, событие, места, `expires_at`, `status`.
Срок — ровно 10 минут от времени PostgreSQL после получения блокировок.
`GET /reservations/{id}` доступен только владельцу.

| Ситуация | Результат |
| --- | --- |
| Одно место занято | `409`; вся группа откатывается |
| Неизвестное место | `404`; частичная бронь не создаётся |
| Событие закрыто или уже началось | `409` |
| Повторяющиеся/пустые места, больше 20 | `422` |
| Чужая группа | `404` |
| Истёкшая бронь | Место сразу доступно, даже если worker ещё не запускался |

Все изменения покупки сначала блокируют событие через `FOR UPDATE`; бронь затем
блокирует инвентарь в порядке UUID. Транзакция короткая, не длится 10 минут.
Это сериализует операции одного события; события обрабатываются независимо.
Выбор сознательно ограничивает параллелизм одного события ради простого общего
порядка блокировок оплаты, истечения и отмены. Срок проверяется через
`clock_timestamp()` после ожидания блокировки, а не временем начала транзакции.
Основа: [блокировки PostgreSQL](https://www.postgresql.org/docs/current/explicit-locking.html)
и [функции времени](https://www.postgresql.org/docs/current/functions-datetime.html).

## Worker

Запусти в отдельном терминале вместе с API:

```sh
uv run --locked python -m ticketflow.worker
```

Разовый запуск: `uv run --locked python -m ticketflow.worker --once`.
Период меняется через `--interval 30` (секунды). SIGINT/SIGTERM завершают процесс.
Одна итерация обрабатывает до 100 событий, отдельной транзакцией для каждого.
ACTIVE переводится в EXPIRED; связанный PENDING-заказ — в CANCELLED.
Повторный запуск безопасен. Корректность брони и оплаты не зависит от запуска worker.
